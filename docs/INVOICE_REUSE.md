# 票面数量、发票占用与成对银行档案

## 数量规则

解析增量保留 `invoice_code/check_code/items[]`，明细含名称、规格型号、单位、数量、单价、金额；原解析接口及用户 AI 选择不变。文本表格先抽取，校对模型补充明细必须有原文证据。

- 单行用票面数量、单位；多行统一数量 `1`、单位 `份/批`。
- 完全缺失时默认 `1 份/批`；只读到数量或单位则保留已读部分、补默认另一部分。不追加数量/单位问答。
- 识别汇总增加可核对的数量/单位；合开固定按批。当前飞书明细没有独立单位字段，使用现有 `规格` 控件承接单位；物品原始规格型号保留在 `items`，不另问。
- 已有草稿中曾填写的数量/规格迁入汇总事实，避免覆盖用户旧填写。未追溯重跑所有历史原件。新解析和新提交以汇总事实为准，忽略过期的逐方式数量答案。

## 查重与读一次

`.expense-data.sqlite3` 新增：

- `invoice_reads(sha256 PK, status, result_json, updated_at)`：成功结果缓存；失败允许重试。线程锁 + 数据库识别租约避免并行重复调用；成功后继续编辑只取缓存。
- `invoice_uses(invoice_key PK, owner, draft_id, invoice_id, phase, project, amount, updated_at)`：唯一占用，phase 为 active/pending/submitted。
- `invoice_registry_meta(id PK)`：首次运行自动索引既有提交历史和进行中草稿。

稳定键为数电20位票号 `digital:number`，或传统票10/12位代码+8位号码 `vat:code:number`；代码/号码已经唯一，不另拼校验码。缺代码的8位号码不作全局唯一键，以免误伤。所有文件另有 `sha:SHA256`。原件按登录用户授权，缓存只能经本人原件引用读取；换账号不借用对方 API 密钥。

范围是本 Mini 本应用数据库内**全部登录用户**的进行中草稿和已提交记录。不是整个飞书审批中心：站外手工审批、其他部署及没有进入本地历史的审批不在此范围。首次索引优先历史；既有重复只保留第一份占用、不删除历史，冲突须人工核对。

上传先检查哈希；原生 PDF 可无 OCR/LLM 读取票号提前检查。不同编码图片必须先识别一次才能获知票号，随后拒绝进入新报销；这个成功识别结果仍缓存，不再次付费识别。不同字节且始终没有稳定票号无法保证识别为同票；不以商户+金额猜测同票。

同一 owner + draft + invoice 行可恢复/复用；同草稿另一行、另一草稿、另一用户均冲突。原件仍保留；晚于上传的票号冲突会移除新增界面行，不静默覆盖。草稿保存、提交前再次在 SQLite 事务内核对，客户端编辑票号不能绕过原件缓存中的身份。删除草稿/移除发票释放 active 占用；提交成功及结果未知的 pending 不释放。明确的飞书拒绝才恢复 active，未知结果需核对原申请，避免重复发单。附件上传后、真正 initiate 之前再次核对草稿版本和删除状态。

## 银行档案

`filling_profiles(id PK, kind, side, title, fields_json, creator, creator_name, revision, active, created_at, updated_at)`。

当前 `kind=bank`；side 为 `ours/counterparty`；fields 为 `{account,bank,holder}`。简称、账号、开户行必填，户名可选（合同审批使用时要求有户名）。其他 kind 留待后续扩展，不做 CRM。

`/api/filling-profiles` 使用现有 OAuth/来源校验，全部本应用登录用户共享读取；仅创建者能 PATCH/DELETE，版本冲突返回409，DELETE 为停用。账号按原需求在本机600权限数据库保存，列表仅展示账号末4位，选择/编辑使用完整账号。停用/修改档案不回写过去报销。

问答把相关银行字段合为一步，直接点已有档案或新增保存并填入；草稿银行字段旁也有入口。保留现有控件 ID：

- 预付款项 `银行账户`、`收款账号` ← account；`开户支行` ← bank。
- 合同审批 `账户名称` ← holder；`收款账号` ← account；`开户支行` ← bank。
- 当前定义只有对方收款字段；我方档案可保存并独立管理，未来出现 `我方/付款` 字段时已有类型映射，不把我方账户误填到收款字段。不新增飞书控件或改变采购定义。

所有验证使用合成数据及模拟飞书响应，不调用真实审批或消息接口。
